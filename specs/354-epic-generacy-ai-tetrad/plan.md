## Summary

Ship a single Claude Code slash command — `/cockpit:review` — as a markdown verb file in the existing `claude-plugin-cockpit` package. The command is a thin orchestrator: it never resolves PRs, runs `/code-review`, or mutates labels directly. Instead it delegates each responsibility to an existing primitive:

- **`--gate impl`** → calls `/cockpit:review-context` (G1.3) for PR resolution, then `/code-review` (host skill) for the diff summary.
- **All other gates** (`specify`, `clarify`, `plan`, `tasks`) → reads exactly one artifact file under `specs/<feature>/` per the locked Q1 mapping and emits a three-section summary (`Blockers`, `Open questions`, `Suggested decision`).
- **On approval** (in `assist`/`auto` modes) → calls `/cockpit:advance --gate <name>` (G1.2), which is the sole owner of the `waiting-for:<name>` → `completed:<name>` label transition.

Modes (`assist` default, `auto`, `manual`) gate whether `AskUserQuestion` is used and whether `/cockpit:advance` is invoked. The command never mutates labels itself and never reimplements logic owned by G1.2 or G1.3.

The entire deliverable is one new file. No package.json, no build step, no MCP coupling — the cockpit plugin scaffold from #350 already supplies the manifest and marketplace entry.

## Implementation Phases

### Phase 0: Verify the host primitives exist

Before writing `review.md`, confirm the four primitives it depends on are actually callable in the Claude Code environment:

1. `/code-review` — confirmed present in the available-skills list as `code-review`.
2. `AskUserQuestion` — confirmed present in the deferred-tools list.
3. `/cockpit:advance` (G1.2) — **not yet landed** at the time of planning. The command must call it by slash invocation, not by reimplementing label mutation. If `/cockpit:advance` is missing at runtime, the command should fail with `Suggested decision: abort` and a clear "dependency not installed" message.
4. `/cockpit:review-context` (G1.3) — **not yet landed**. Same fallback as #3.

These are runtime dependencies, not build-time ones: the markdown file can land independently and will simply fail-fast at first call if the dependencies are missing.

### Phase 1: Author `commands/review.md`

Write the verb file with this structure:

1. **YAML frontmatter** — `description:` matching the README row text.
2. **Argument parsing** — explicit handling of:
   - `--gate <name>` (required; valid set: `specify`, `clarify`, `plan`, `tasks`, `impl`).
   - `--mode <assist|auto|manual>` (optional; default `assist`).
   - bare invocation / `--help` → list gates + modes (FR-010).
3. **Gate dispatch**:
   - `impl` branch: call `/cockpit:review-context`, then `/code-review` on the returned diff, then emit the summary verbatim with a `Suggested decision:` line appended if `/code-review` doesn't already provide one.
   - Non-`impl` branch: resolve the artifact path per the Q1 mapping table, read it, emit three sections (`Blockers`, `Open questions`, `Suggested decision`), end with the standard final line.
4. **Mode handling**:
   - `assist`: call `AskUserQuestion` with three options (approve / request-changes / abort). On `approve`, call `/cockpit:advance --gate <name>` and report the label transition.
   - `auto`: if `Suggested decision: approve`, call `/cockpit:advance` without prompting; otherwise stop with the open items.
   - `manual`: emit summary only; never call `/cockpit:advance`.
5. **Failure modes** (FR-009):
   - Unknown gate → list valid gates, exit.
   - Unknown mode → list valid modes, exit.
   - `impl` gate but review-context returns no/multi PR → surface its message verbatim, exit with no label changes.
   - Non-`impl` gate but artifact missing → name the expected file path, exit with no label changes.

### Phase 2: README touch-up (optional in this issue)

Flip the `/cockpit:review` row in `packages/claude-plugin-cockpit/README.md` from "(coming in #351–#360)" to a live one-line description. This is cosmetic; if deferred, it can ship in the same PR as G1.2/G1.3 land.

### Phase 3: Manual validation (per Success Criteria)

5. SC-001: After plugin install, confirm `/cockpit:review` shows up in the slash-command palette.
6. SC-002: Run `/cockpit:review --gate impl` against a real child issue/PR; verify the `/code-review` summary appears and that approval drives the labels via `gh issue view`.

9. SC-005: `grep` the transcripts for the `Suggested decision:` final line.

## Open Risks

| Risk | Mitigation |
|------|------------|
| `/cockpit:advance` (#788) or `/cockpit:review-context` (#789) lands with a different surface than assumed | This command does not couple to their internals — it calls them by slash name and surfaces their output verbatim. Any contract drift surfaces as a runtime error, not a silent miscommunication. |
| `AskUserQuestion` is not available in some non-interactive Claude Code environments | `assist` mode degrades gracefully: detect missing prompt primitive → fall back to `manual` mode with a "re-run with --mode auto to advance" hint. |
| `/code-review` summary already ends with a `Suggested decision:` line and we append a second one | The `impl` branch should detect and reuse `/code-review`'s line rather than appending. Spec calls for "surfaces its summary verbatim" (FR-003) — verbatim wins; only append if absent. |
| Multiple speckit features on the same branch (rare but possible) | Use the cockpit branch-naming convention (`<issue#>-*`) to pick the matching `specs/<feature>/` directory. If ambiguous, fail-fast with the list of candidate directories. |
