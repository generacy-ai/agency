## Resolved Clarifications

The following design decisions were resolved in clarification batch 1 (2026-06-26). See [clarifications.md](./clarifications.md) for full context.

- **Partial-approval semantics (Q1)**: The command posts the approved subset on every run, but only invokes `generacy cockpit advance --gate clarification` once every open question has an approved answer in the current run. No premature gate advance with gaps; the "approve all" case posts and advances in a single invocation.
- **Canonical comment marker (Q2)**: Posted comments carry the HTML marker `<!-- generacy-cockpit:clarification-answers -->` on the first line. This marker identifies cockpit-authored answer comments; orchestrator resume itself is triggered by the `completed:clarification` label, not by the marker.
- **Issue-resolution behavior (Q3)**: The command accepts an explicit issue argument in v1 (`/cockpit:clarify <issue>`, used by `/cockpit:watch`). Branch inference from the `###-*` convention is a fallback. If neither resolves a target issue, the command exits with a hard error and guidance to pass `--issue <n>`.
- **Drafting fallback for ungrounded questions (Q4)**: When the agent cannot ground an answer in `spec.md`, `plan.md`, or repository code, that question is rendered as an explicitly-marked stub (`_no draft — insufficient context_`). The developer can fill it in, edit it, or skip it; the rest of the batch continues normally rather than blocking on the un-drafted question.
- **Comment-posting transport (Q5)**: The command posts the marked answer comment via `gh issue comment` directly. `gh` becomes a hard runtime dependency of `/cockpit:clarify`. Gate advance still goes through the existing `generacy cockpit advance` verb (G1.2 / #788 is not extended with a posting subcommand).
