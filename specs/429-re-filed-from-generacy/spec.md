## Root defect — Leg 1 reads a non-existent `response.comments` field

The postcondition's Leg 1 compares the count of inline comments against the POST response of `POST /repos/{o}/{r}/pulls/{n}/reviews`:

- `packages/claude-plugin-cockpit/commands/auto.md:305` — `**Leg 1** — response.comments.length == bundle.comments.length`
- `specs/422-summary-auto-md-s/contracts/postcondition-check.md` § Leg 1 — same rule

That response object has **no `comments` field**. Observed keys: `_links, author_association, body, commit_id, html_url, id, node_id, pull_request_url, state, submitted_at, user`. So `response.comments` is `undefined` and `undefined.length` throws / the comparison fails on **every successful POST**.

### Impact

On each successful `request-changes` POST, a literal implementation:

1. Leg 1 reads `undefined` → postcondition "fails" → guardrail sleeps 2000 ms and **retries the POST once (posting a duplicate review)**, then "fails" again →
2. re-presents the G.2 verdict gate with a spurious `postcondition failed after retry` notice, even though the review landed perfectly.

The guardrail as literally specified never confirms a real success and double-posts reviews. (In the snappoll run — christrudelpw/snappoll#2, #7, #8, #13 — this was worked around by verifying against the correct fields by hand, so no double-posts occurred; but that required *not* following the contract verbatim.)

## Fix

In `contracts/postcondition-check.md` § Leg 1 and the D.2 prose (`auto.md:305`):

- Verify inline comments via a **separate** endpoint — `GET /repos/{o}/{r}/pulls/{n}/comments` — filtered to `pull_request_review_id == response.id`, and compare *that* count to `bundle.comments.length`. Do **not** read `response.comments`.

## Leg 2 — likely already consistent, add a belt-and-suspenders match

The original report also flagged Leg 2 (`comments.nodes[0].author.login == <acting-bot-login>`) as failing because the bot login renders differently across APIs (REST `generacy-ai[bot]` vs GraphQL `generacy-ai`). On close reading, the contract's Leg 2 is **GraphQL-to-GraphQL**: `auto.md:330` binds `<acting-bot-login>` to the GraphQL `viewer.login` and compares it to the GraphQL `reviewThreads…author.login`. Both render `generacy-ai`, so the `==` as specified should match — the REST `generacy-ai[bot]` form is never on either side of the comparison.

Recommend a **suffix-insensitive** match anyway (strip a trailing `[bot]` before comparing) as defense-in-depth against an implementation that binds `<acting-bot-login>` to a REST-derived login — but treat **Leg 1 as the must-fix**; Leg 2 is a hardening.

## Acceptance criteria

- [ ] A successful single-comment `request-changes` POST passes the postcondition on the **first** attempt (no retry, no re-present) — verified end-to-end against a real PR.
- [ ] The postcondition never reads a non-existent `response.comments` field; Leg 1 counts via `GET …/pulls/{n}/comments` filtered on `pull_request_review_id == response.id`.
- [ ] The Leg 2 author match treats `generacy-ai` and `generacy-ai[bot]` as the same identity.
- [ ] A regression test asserts the postcondition passes for a known-good POST and fails only when the review genuinely did not land.
