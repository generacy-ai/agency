# Research: Tool Registry and Naming Convention

## Technology Decisions

### 1. Validation Architecture

**Decision**: Separate validation logic into `validation.ts` module

**Rationale**:
- Single responsibility: registry manages storage, validation.ts handles name rules
- Enables reuse: validation can be called independently (e.g., in builders)
- Easier testing: validation logic can be unit tested in isolation
- Follows existing codebase pattern (e.g., config/schema.ts separate from config/loader.ts)

**Alternatives Considered**:
- Inline validation in registry methods: Rejected (coupling, harder to test)
- Validation class: Rejected (overkill for stateless functions)

### 2. Prefix Storage

**Decision**: Simple `const` array with `as const` assertion

```typescript
const STANDARD_PREFIXES = ['source_control', 'build', ...] as const;
```

**Rationale**:
- Type-safe: generates union type for autocomplete
- Simple: no runtime overhead, easy to maintain
- Extensible: can be extended via `[...STANDARD_PREFIXES, 'custom']`

**Alternatives Considered**:
- Enum: Rejected (poor tree-shaking, verbose)
- Configuration file: Rejected (overkill for static list, per spec this is fixed for initial release)
- Registry method to add prefixes: Rejected (complexity, unclear ownership)

### 3. Warning Mechanism

**Decision**: Return warnings in `ValidationResult.warnings` array

**Rationale**:
- Programmatic: consumers can filter/log/ignore as needed
- Testable: easy to verify warning generation in tests
- Non-blocking: validation still returns `valid: true` with warnings
- Consistent with error handling pattern

**Alternatives Considered**:
- console.warn directly: Rejected (not programmatic, can't suppress)
- Event emitter: Rejected (overkill for simple warnings)
- Separate warning callback: Rejected (complicates API)

### 4. Duplicate Registration Handling

**Decision**: Replace tool and log warning via `console.warn`

**Rationale**:
- Non-blocking: legitimate plugin override use case
- Visible: developers see conflict during development
- Per spec: "Replace with warning - log that a tool was overwritten"

**Implementation**:
```typescript
register(tool: AgencyTool): void {
  const existing = this.tools.get(tool.name);
  if (existing) {
    console.warn(`Tool '${tool.name}' overwritten (was from plugin: ${existing.plugin})`);
  }
  this.tools.set(tool.name, tool);
}
```

### 5. Catalog Format

**Decision**: JSON object with `byPrefix` grouping, ISO timestamp

**Rationale**:
- Single source of truth (per clarification)
- Efficient lookup by prefix
- Timestamp enables cache invalidation

**Structure**:
```typescript
{
  tools: [...],
  byPrefix: {
    'source_control': [...],
    'build': [...]
  },
  generatedAt: '2026-01-17T00:00:00.000Z'
}
```

## Implementation Patterns

### snake_case Validation

Use regex for performance and clarity:

```typescript
const SNAKE_CASE_PATTERN = /^[a-z][a-z0-9]*(_[a-z0-9]+)*$/;
```

Rules:
- Must start with lowercase letter
- Can contain lowercase letters and digits
- Underscores separate segments
- No consecutive underscores
- No trailing underscores

### Prefix Extraction

Simple split with validation:

```typescript
function extractParts(name: string): { prefix: string; action: string } | null {
  const parts = name.split('.');
  if (parts.length !== 2) return null;
  return { prefix: parts[0], action: parts[1] };
}
```
