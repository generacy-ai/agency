# Implementation Plan: Integrate Execution Lease Protocol into Orchestrator Dispatch

**Feature**: Modify the orchestrator dispatch pipeline to request execution leases from the cloud before dispatching work to workers, enforcing tier-based concurrency limits
**Branch**: `327-context-part-billing`
**Status**: Complete

## Summary

Add execution lease enforcement to the orchestrator's `WorkerDispatcher`. Before dispatching a queue item to a worker, the dispatcher must request a lease from the cloud via the WebSocket relay. Leases are maintained via heartbeats and released on workflow completion, failure, pause, or cancel. The cloud can push `slot_available` notifications to trigger dispatch of queued items when capacity frees up. This is **Phase 3** of the Billing & Concurrent Workflow Enforcement plan.

**Important**: The orchestrator lives in the `generacy` repo (`packages/orchestrator/`), not in this repo. This plan documents the implementation approach; the actual code changes will be in `generacy`.

## Technical Context

**Language/Version**: TypeScript (Node.js)
**Primary Repository**: `generacy` (`packages/orchestrator/`, `packages/cluster-relay/`)
**Primary Dependencies**: `@generacy-ai/cluster-relay` (WebSocket relay), Redis (queue), Vitest (testing)
**Cloud Dependency**: `ExecutionLeaseService` in `generacy-cloud` (Phase 2 — already implemented)
**Target Platform**: Orchestrator service running in Kubernetes
**Testing**: Unit tests (Vitest) with mocked relay, queue, and Redis
**Constraints**:
- Fail-closed: if lease request times out (30s), treat as denied
- Graceful pause on heartbeat failure: let current task finish, then pause
- Sequential multi-slot dispatch (not parallel)
- No retry logic for transient relay failures (out of scope)

## Implementation Approach

### Phase A: Relay Message Types

Extend `cluster-relay/src/messages.ts` to add six new message types to the `RelayMessage` discriminated union:

- `lease_request` (Cluster → Cloud)
- `lease_granted` (Cloud → Cluster)
- `lease_denied` (Cloud → Cluster)
- `lease_release` (Cluster → Cloud)
- `lease_heartbeat` (Cluster → Cloud)
- `slot_available` (Cloud → Cluster)

### Phase B: Lease Manager Service

Create `LeaseManager` class (`services/lease-manager.ts`) to encapsulate lease lifecycle:

1. **`requestLease(queueItemId, jobId)`** — sends `lease_request` via relay, returns promise that resolves on `lease_granted`/`lease_denied` or rejects on 30s timeout
2. **`releaseLease(leaseId)`** — sends `lease_release` via relay
3. **`startHeartbeat(leaseId)`** — starts 30s interval sending `lease_heartbeat`, returns cleanup function
4. **`handleHeartbeatFailure(leaseId)`** — triggers graceful pause (stop new dispatches, let current task finish)
5. **Active lease tracking** — `Map<leaseId, LeaseInfo>` for correlation

The manager holds a reference to the relay client and uses correlation IDs to match requests to responses.

### Phase C: WorkerDispatcher Integration

Modify `WorkerDispatcher.pollOnce()`:

1. After `queue.claim()` succeeds, call `leaseManager.requestLease()`
2. On `lease_granted`: store `leaseId` in `WorkerInfo`, start lease heartbeat, dispatch to handler
3. On `lease_denied`: call `queue.release()` to put item back, skip dispatch
4. On handler complete/fail: call `leaseManager.releaseLease()`, stop heartbeat

### Phase D: RelayBridge Integration

Modify `RelayBridge` to:

1. Route incoming `lease_granted`, `lease_denied` messages to `LeaseManager`
2. Listen for `slot_available` messages and trigger `WorkerDispatcher` to attempt dispatch for up to `availableSlots` items sequentially
3. Forward outgoing `lease_request`, `lease_release`, `lease_heartbeat` messages through the relay client

### Phase E: Configuration

Add to `DispatchConfig`:

```typescript
leaseRequestTimeoutMs: number;     // Default: 30000 (30s)
leaseHeartbeatIntervalMs: number;  // Default: 30000 (30s)
leaseEnabled: boolean;             // Default: false (feature flag for rollout)
```

### Phase F: Tests

Unit tests covering:
- Lease request → granted → dispatch flow
- Lease request → denied → item stays queued
- Lease request → timeout → treated as denied
- Lease release on workflow complete/fail/pause/cancel
- Heartbeat loop lifecycle (start, refresh, stop)
- Heartbeat failure → graceful pause
- `slot_available` → sequential multi-slot dispatch
- Feature flag off → dispatch without lease (backward compatibility)

## Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Separate `LeaseManager` class | Extract from dispatcher | Single Responsibility; keeps dispatcher focused on queue polling, lease logic isolated and testable |
| Correlation-based request/response | Use `correlationId` in relay messages | Matches existing `api_request`/`api_response` pattern in relay protocol |
| Feature flag `leaseEnabled` | Config-driven opt-in | Safe rollout — existing clusters work without leases until enabled |
| 30s timeout fail-closed | Treat timeout as denied | Prevents unbounded blocking; fail-open would defeat concurrency enforcement |
| Graceful pause on heartbeat failure | Let current task finish | Prevents repo corruption from interrupted operations |
| Sequential slot dispatch | One lease request at a time | Prevents over-commit; each request changes available count |
