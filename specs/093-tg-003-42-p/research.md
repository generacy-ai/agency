# Research: Type Definitions

## Technology Decisions

### TypeScript Strict Mode
**Decision**: Enable all strict mode flags
**Rationale**: Catch errors early, enforce type safety, improve maintainability
**Alternatives Considered**:
- Gradual strict mode adoption: Rejected - better to start strict
- Loose mode: Rejected - defeats purpose of TypeScript

### Runtime Validation with Zod
**Decision**: Use Zod for runtime validation at boundaries
**Rationale**: Type-safe schema validation, automatic type inference, excellent DX
**Alternatives Considered**:
- `io-ts`: More complex, less intuitive API
- `yup`: Not TypeScript-first, weaker type inference
- Manual validation: Error-prone, verbose

### Discriminated Unions for State
**Decision**: Use tagged unions for state machines
**Rationale**: Type-safe exhaustiveness checking, clear state transitions
**Pattern**:
```typescript
type PluginState =
  | { status: 'loading' }
  | { status: 'ready'; manifest: PluginManifest }
  | { status: 'error'; error: Error }
```

### Branded Types for IDs
**Decision**: Use branded types for entity identifiers
**Rationale**: Prevent accidental ID mixing (plugin ID vs tool ID)
**Pattern**:
```typescript
type PluginId = string & { readonly __brand: 'PluginId' }
type ToolId = string & { readonly __brand: 'ToolId' }
```

## Implementation Patterns

### Type Organization
- **One domain per file**: Each type file covers a cohesive domain
- **Barrel exports**: Central index.ts for clean imports
- **Dependency order**: Avoid circular dependencies

### Documentation Style
- **JSDoc for all public types**: Enables IntelliSense
- **Examples in comments**: Show common usage patterns
- **Link to specs**: Reference design decisions

### Immutability
- Use `readonly` for data structures
- Use `ReadonlyArray<T>` over `T[]` for immutable lists
- Use `Readonly<T>` for object snapshots

## Type System Boundaries

### Trust Boundaries
- **Internal**: Strong typing, prefer compile-time checks
- **External**: Runtime validation with Zod at entry points
- **VS Code API**: Trust VS Code types, no additional validation

### Validation Strategy
```typescript
// External data (user input, MCP responses, config files)
const pluginConfigSchema = z.object({
  id: z.string(),
  enabled: z.boolean(),
  settings: z.record(z.unknown())
})

// Internal types derived from schemas
type PluginConfig = z.infer<typeof pluginConfigSchema>
```
