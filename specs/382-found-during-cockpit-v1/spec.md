## Summary

Found during the cockpit v1 integration smoke test (generacy-ai/tetrad-development#88), findings #12-14 — all in claude-plugin-cockpit's review/watch playbooks, discovered running the first live `/cockpit:review --gate impl`.

**1. Gate-token misalignment (three vocabularies for one gate).** The CLI's gate vocabulary derives names from label pairs, so the only valid token is `implementation-review` (`generacy cockpit advance --help-gates`). But review.md accepts/documents `--gate impl`, its header mapping ("waiting-for:<gate>-review → /cockpit:review --gate <gate>") implies `implementation`, and watch.md's suggestion table emitted BOTH `--gate impl` and `--gate implementation` at different transitions in one session. The session agent had to self-correct mid-advance. Fix: one vocabulary everywhere — the CLI's gate names verbatim (`implementation-review`, `plan-review`, ...) in review.md's accepted values, watch.md's suggestion table, and all examples. If a short alias is wanted, the CLI's vocabulary is the place to add it (single source), not the markdown.

**2. request-changes path delivers nothing.** review.md step 7: on `request-changes`, "emit no Labels: line, mutate no state, exit zero" — a silent no-op. The reviewer's findings never reach the worker; the session agent improvised a top-level PR comment, which the PrFeedbackMonitorService cannot see (it triggers on PR review events with unresolved review THREADS). Fix: on request-changes, post a PR review with `event: COMMENT` and one inline comment per finding (file:line-anchored — /code-review findings carry anchors already), via `gh api repos/{owner}/{repo}/pulls/{n}/reviews`. COMMENT-event reviews are permitted on one's own PR (only APPROVE/REQUEST_CHANGES are blocked), so this works on single-credential clusters — and it triggers the EXISTING feedback flow: PrFeedbackMonitorService detects the unresolved threads → applies waiting-for:address-pr-feedback → enqueues the fix work → agent replies per thread. No new label, no protocol change (an explicit changes-requested label was considered and rejected: the thread-based signal already exists and drives the whole downstream handler).

**3. Suggested-decision derivation makes every finding blocking.** review.md step 3: "any blockers → request-changes; non-blocking findings only → request-changes; no findings → approve". The middle rule contradicts the blocking/non-blocking distinction it depends on — observed live: two explicitly minor findings produced a request-changes suggestion the operator had to override. Fix: non-blocking findings only → approve (with the findings included in the review-comment body posted on approval, or carried as COMMENT-review threads without blocking the gate).

Owns: packages/claude-plugin-cockpit/{commands/review.md,commands/watch.md,README.md}. The rev 3 catalog's `--gate impl` shorthand (origin of vocabulary #1) is corrected in tetrad-development's plan doc separately.
