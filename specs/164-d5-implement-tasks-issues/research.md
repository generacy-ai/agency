# Research: D5 Implement tasks_to_issues Tool

## Technology Decisions

### 1. GitHub Integration Approach
**Decision**: Direct GitHub CLI (gh) integration

**Rationale**:
- Simpler implementation matching reference
- gh CLI handles authentication, rate limiting, pagination
- No need for OAuth token management
- Consistent with other speckit tools

**Alternatives Considered**:
- BacklogProvider abstraction (more complex, delayed benefit)
- Direct GitHub REST API (more code, auth complexity)

### 2. Task Parsing Strategy
**Decision**: Embed parsing logic in this tool

**Rationale**:
- Self-contained implementation
- No external dependencies
- Can be refactored later if B5 (task-parser) is implemented
- Parsing logic is relatively simple

**Alternatives Considered**:
- Wait for B5 module (creates blocking dependency)
- Use external markdown parser (overkill for this use case)

### 3. Task Format Support
**Decision**: Support both T### and TG-XXX formats

**Rationale**:
- Full feature parity with reference implementation
- TG-XXX is essential for epic workflows
- Format detection is straightforward
- Separate parsing paths keep code clean

## Implementation Patterns

### Reference Implementation Analysis
The reference implementation at `/workspaces/claude-plugins/plugins/speckit/mcp-server/src/tools/tasks-to-issues.ts` provides:

1. **Modular Structure**
   - Separate utilities for parsing, grouping, dependencies, GitHub
   - Clean separation of concerns
   - Testable components

2. **Error Handling Pattern**
   - Structured error objects with codes
   - Retryable flag for transient errors
   - Graceful degradation (partial failures)

3. **Review Gate Pattern**
   - Check labels before execution
   - Block on epic without approval
   - Allow bypass for non-epic issues

### Grouping Strategies

| Strategy | Use Case | Granularity |
|----------|----------|-------------|
| per-task | Maximum visibility, small tasks | Finest |
| per-story | Balanced, story-based work | Medium |
| per-phase | Large epics, phase milestones | Coarsest |

### Dependency Handling

1. **Explicit Dependencies**
   - `(deps: T001, T002)` in task description
   - `(depends-on: T001)` marker

2. **Auto-Generated Dependencies** (optional)
   - Cross-phase: Phase N depends on Phase N-1
   - Sequential: Within-phase ordering

3. **Resolution**
   - Task ID → Group ID → Issue Number
   - Include `<!-- depends-on: #123 -->` in issue body

## Risk Mitigation

### GitHub API Rate Limits
- Implement exponential backoff (1s, 2s, 4s, max 10s)
- Retry on 429 status codes
- Log rate limit headers

### Circular Dependencies
- Detect during validation phase
- Clear error messages with cycle visualization
- Block issue creation on circular deps

### Partial Failures
- Continue creating remaining issues
- Track created vs failed
- Include failure details in result

### Large Task Files
- Efficient single-pass parsing
- Stream-friendly design
- Memory-bounded operations
