### Q1: Pin test vs explicit prohibition conflict
**Context**: FR-003 requires step 5 to explicitly name the files the plan phase must never modify (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.github/copilot-instructions.md`), but FR-004 and SC-001 require `grep -i "claude.md\|update_agent"` over both plan.md copies to return zero matches. These cannot both hold: naming CLAUDE.md in the prohibition sentence creates a grep match. Additionally, FR-003's natural phrasing "agent-context files" (hyphenated) would evade a literal "agent context" ban while violating its intent.
**Question**: How should this conflict be resolved — may the prohibition sentence name the forbidden files literally (with the pin test and SC-001 grep tightened around that one exception), or must the command text avoid the literal filenames entirely?
**Options**:
- A: Prohibition names the files explicitly; pin test bans `update_agent` everywhere but allows `CLAUDE.md`/"agent context" only within the single NEVER-modify sentence; SC-001 grep adjusted to match.
- B: Keep zero-match grep as written; the prohibition refers generically to "repo-root agent instruction files" without literal filenames (weakens FR-003's explicitness).
- C: Ban only `update_agent`; drop `CLAUDE.md`/"agent context" from the banned list and rely on positive assertions about the new step 5 text instead.

**Answer**: A — the prohibition names the files explicitly; the pin test bans `update_agent` everywhere but allows the filenames and the phrase "agent context" only within the single NEVER-modify sentence; adjust SC-001's grep to match. Rationale: the conflict is a flaw in the issue's acceptance criterion, not the design — explicitness is the whole mechanism, since the model hand-writes CLAUDE.md prose precisely when the instruction is vague. (Answered by @christrudelpw on GitHub, 2026-08-28)

### Q2: stack.md re-run semantics
**Context**: /plan can run more than once on the same feature branch (e.g., re-plan after clarifications). The new step 5 text must tell the agent whether `specs/<feature>/stack.md` is regenerated or accumulated, and the required header "Generated by /plan — do not hand-edit." implies the command owns the file.
**Question**: When /plan runs again for the same feature, should stack.md be fully overwritten or appended to?
**Options**:
- A: Overwrite — stack.md always reflects the latest plan run; history lives in git.
- B: Append — each run adds a new timestamped section preserving prior context.

**Answer**: A — overwrite; stack.md always reflects the latest plan run, history lives in git. Rationale: appending is the exact accumulating-log pathology this epic exists to eliminate, merely relocated; the "Generated by /plan — do not hand-edit." header declares command ownership, and `git log -p` recovers prior runs. (Answered by @christrudelpw on GitHub, 2026-08-28)

### Q3: Positive assertions in pin test
**Context**: US2's acceptance criteria only assert absence of the old strings plus byte-identity of the two copies. If step 5 were deleted wholesale, or the stack.md instruction dropped, those assertions would still pass while the intended behavior regresses silently.
**Question**: Should the pin test also positively assert the new contract — that both copies instruct writing `specs/<feature>/stack.md`, include the required header line, and contain the prohibition statement?
**Options**:
- A: Yes — assert presence of the stack.md instruction, header line, and prohibition, alongside the absence and identity checks.
- B: No — absence + byte-identity checks only, as currently specified.

**Answer**: A — yes; assert presence of the stack.md instruction, the required header line, and the prohibition statement alongside the absence and byte-identity checks. Rationale: absence-only assertions pass when step 5 is deleted wholesale — the same false-confidence failure mode as the #899 guard; positive assertions match this repo's pin philosophy (pins assert the exact contract). (Answered by @christrudelpw on GitHub, 2026-08-28)

### Q4: Changeset bump level
**Context**: FR-006 requires a changeset covering both spec-kit packages but does not specify the semver bump. The change alters shipped command behavior (plan-phase output location) without changing any public API.
**Question**: Which bump level should the changeset use for both packages?
**Options**:
- A: patch — it fixes incorrect behavior of the existing /plan command.
- B: minor — it changes user-visible behavior of the plan phase (new stack.md artifact).

**Answer**: B — minor, for both spec-kit packages. Rationale: not purely a fix — the command stops producing one output (CLAUDE.md updates) and starts producing another (`specs/<feature>/stack.md`); workflows reading the old output see a behavior change, which deserves more changelog visibility than a patch line. (Answered by @christrudelpw on GitHub, 2026-08-28)
