# Research: Build Dependency Ordering

## Technology Decision

### Turborepo Build Ordering

**Decision**: Add workspace dependency to `devDependencies` in addition to `peerDependencies`

**Rationale**:
- Turborepo's `^build` operator only considers `dependencies` and `devDependencies`
- peerDependencies are designed for runtime requirements, not build-time ordering
- This is the [documented pattern](https://turbo.build/repo/docs/core-concepts/monorepos/configuring-workspaces#depending-on-other-workspaces-in-the-monorepo) for TypeScript monorepos

### Alternatives Considered

| Approach | Pros | Cons | Decision |
|----------|------|------|----------|
| Add to devDependencies | Standard pattern, minimal change, works with Turbo | Duplicates in peerDeps and devDeps | **Selected** |
| Remove peerDependencies | Simpler structure | Loses semantic meaning for consumers | Rejected |
| Add explicit Turbo task ordering | More explicit control | Harder to maintain, doesn't scale | Rejected |
| Use TypeScript project references | Native TS solution | Requires tsconfig changes across all packages | Rejected |

## Implementation Pattern

### Standard Monorepo Plugin Pattern

```json
{
  "peerDependencies": {
    "@generacy-ai/agency": "workspace:*"
  },
  "devDependencies": {
    "@generacy-ai/agency": "workspace:*"
  }
}
```

This pattern is used by:
- Turborepo examples
- pnpm workspace documentation
- Rush monorepo guidelines

### Why Both?

1. **peerDependencies**: Tells npm/pnpm that consumers must provide this package at runtime
2. **devDependencies**: Enables TypeScript to resolve types during development/build
