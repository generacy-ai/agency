# Feature Specification: Auto-scale worker count down to tier limit

**Branch**: `329-context-part-billing` | **Date**: 2026-03-21 | **Status**: Draft

## Summary

Cap the orchestrator's effective worker count at the minimum of the locally configured worker count and the subscription tier's concurrent execution limit. Part of [Billing & Concurrent Workflow Enforcement](https://github.com/generacy-ai/tetrad-development/blob/develop/docs/billing-concurrent-workflow-enforcement.md) — **Phase 3: Orchestrator Integration**.

## Context

The billing system enforces concurrent execution limits per subscription tier. The orchestrator must respect these limits by auto-scaling down the number of active worker containers when the tier limit is lower than the locally configured worker count. It must also handle `cluster_rejected` errors when the cluster limit has been reached.

## User Stories

### US1: Worker auto-scale down

**As a** developer using the orchestrator,
**I want** the system to automatically cap my active workers to my subscription tier's limit,
**So that** I don't exceed my billing plan's concurrent execution allowance without needing to manually adjust configuration.

**Acceptance Criteria**:
- [ ] Effective workers = `min(configuredWorkers, tierLimit)`
- [ ] Only `tierLimit` worker containers are actively used when `configuredWorkers > tierLimit`
- [ ] The orchestrator never scales up beyond `configuredWorkers` (local config reflects resource constraints or developer preference)

### US2: Tier limit sync

**As a** developer who upgrades or downgrades my subscription,
**I want** the orchestrator to dynamically adjust the effective worker count when my tier limit changes,
**So that** I can immediately take advantage of a higher limit or comply with a lower one without restarting.

**Acceptance Criteria**:
- [ ] Tier limit fetched from the cloud (via relay or cached subscription data) on startup
- [ ] Tier limit updated when a subscription change notification is received
- [ ] Effective worker count re-calculated on tier limit change

### US3: Cluster rejection handling

**As a** developer who has reached my cluster limit,
**I want** a clear error message when my relay connection is rejected with `cluster_rejected`,
**So that** I understand the problem and know how to resolve it (e.g., by upgrading my plan).

**Acceptance Criteria**:
- [ ] `cluster_rejected` rejection surfaces a user-facing error message
- [ ] Error message includes the current limit
- [ ] Error message suggests upgrading the subscription

## Assumptions

- The relay or subscription data API provides the tier's concurrent execution limit
- Subscription change notifications are delivered via an existing event/message channel
- The orchestrator already has a mechanism for managing worker container lifecycle (start/stop)

## Out of Scope

- Billing integration beyond reading the tier limit (payment processing, plan management)
- UI for displaying or managing worker counts
- Horizontal scaling across multiple orchestrator instances
- Rate limiting or throttling of individual workflow executions
