# Research: Three-Layer Decision Model

## Technology Decisions

### 1. Schema Definition Approach

**Decision**: Define TypeScript interfaces with Zod schemas locally

**Rationale**:
- Zod already used throughout the codebase for validation
- Provides runtime validation + TypeScript inference
- Can be refactored to import from contracts#27 when ready

**Alternatives Considered**:
- JSON Schema: More portable but requires separate TS types
- io-ts: Functional approach, steeper learning curve
- Wait for contracts#27: Would block development unnecessarily

### 2. Decision Storage

**Decision**: In-memory storage with Map-based DecisionStore

**Rationale**:
- Simple for initial implementation
- No external dependencies
- Sufficient for development/testing phase
- Can be replaced with persistent storage later

**Alternatives Considered**:
- File-based storage: More complex, not needed yet
- External database: Overkill for plugin scope
- No storage: Would break outcome reporting workflow

### 3. Backward Compatibility Strategy

**Decision**: Extend existing types with optional fields

**Rationale**:
- Per clarification Q3: Single tool approach is cleaner
- All new fields optional = no breaking changes
- Three-layer response only when explicitly requested

**Implementation Pattern**:
```typescript
// Existing call still works
request_decision({ question: "...", options: [...] })

// Enhanced call with three-layer
request_decision({
  question: "...",
  options: [...],
  domain: ["backend"],
  includeRecommendations: true
})
```

### 4. Pass-Through Architecture

**Decision**: Plugin orchestrates, doesn't compute recommendations

**Rationale**:
- Per clarification Q1: Baseline/protégé come from external services
- Keeps plugin focused on human interaction
- Aligns with separation of concerns in Generacy architecture

**Flow**:
```
Agent → request_decision(includeRecommendations: true)
         ↓
Humancy Plugin → sends request via channel
         ↓
External Service → computes baseline + protégé
         ↓
Human Portal → displays three-layer, collects decision
         ↓
Plugin ← receives complete response with all layers
         ↓
Agent ← returns enhanced response
```

## Implementation Patterns

### Tool Factory Pattern

Follow existing pattern from `createRequestDecisionTool`:

```typescript
export function createNewTool(
  coreAPI: AgencyCoreAPI,
  detector: ConnectionModeDetector,
  store: DecisionStore  // New dependency
): AgencyTool {
  return {
    name: 'humancy.new_tool',
    description: '...',
    namespace: 'humancy',
    outputPattern: 'terse',
    inputSchema: { ... },
    async execute(params: unknown): Promise<ToolResult> {
      // 1. Validate params with Zod
      // 2. Check connection mode
      // 3. Build request
      // 4. Send via channel
      // 5. Wait for response
      // 6. Return terse result
    }
  };
}
```

### Terse Output Pattern

All tools use TerseOutput for consistent responses:

```typescript
// Success
TerseOutput.success(`Decision recorded: ${decisionId}`)

// Failure
TerseOutput.failure(`Decision not found: ${decisionId}`)

// With data
TerseOutput.success(
  `Outcome reported for ${decisionId}`,
  { decisionId, outcome: 'success' }
)
```

### Schema Extension Pattern

Extend existing Zod schemas without breaking changes:

```typescript
// Original
export const decisionOptionSchema = z.object({
  id: z.string().min(1),
  label: z.string().min(1),
  description: z.string().optional(),
});

// Extended (backward compatible)
export const enhancedDecisionOptionSchema = decisionOptionSchema.extend({
  tradeoffs: tradeoffsSchema.optional(),
});
```

## Open Questions Resolved

| Question | Resolution |
|----------|------------|
| Who computes recommendations? | External services (pass-through) |
| What does get_decision_outcome return? | Full decision record with outcome |
| v2 or enhance existing? | Enhance existing request_decision |
| Wait for contracts#27? | No, define locally, align later |
| Where does decisionId come from? | Generated by service, returned in response |
