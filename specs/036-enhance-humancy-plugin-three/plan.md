# Implementation Plan: Enhance humancy plugin for three-layer decision model

**Feature**: Three-layer decision model support for human-agent decisions
**Branch**: `036-enhance-humancy-plugin-three`
**Status**: Complete

## Summary

Enhance the existing humancy plugin to support the three-layer decision model (baseline → protégé → human). This involves:
1. Extending the `request_decision` tool with optional domain, context, and recommendation parameters
2. Adding new tools for decision outcome tracking (`get_decision_outcome`, `report_decision_result`)
3. Creating local TypeScript schemas for the three-layer model (to align with contracts#27 later)

## Architecture Decisions

### AD-1: Pass-through Architecture
**Decision**: Plugin acts as orchestration layer, not AI/ML system
**Rationale**: Per clarification Q1, baseline and protégé recommendations come from external services
**Impact**: Plugin receives pre-computed recommendations and passes them through

### AD-2: Single Tool Enhancement
**Decision**: Enhance existing `request_decision` instead of creating `request_decision_v2`
**Rationale**: Per clarification Q3, adding optional parameters maintains backward compatibility
**Impact**: All new fields are optional; three-layer response only when `includeRecommendations: true`

### AD-3: Local Schema Definition
**Decision**: Define three-layer schemas locally, align with contracts#27 later
**Rationale**: Per clarification Q4, avoids blocking on external dependency
**Impact**: Mark schemas with TODO comments for future alignment

### AD-4: Service-Generated Decision IDs
**Decision**: `decisionId` is generated by humancy service and returned in response
**Rationale**: Per clarification Q5, enables reliable correlation for outcome reporting
**Impact**: Response always includes `decisionId` for use with `report_decision_result`

## Implementation Phases

### Phase 1: Schema Foundation
- Create `three-layer.ts` with recommendation types

- Add Zod schemas with validation
- Update type exports

### Phase 2: Request/Response Enhancement
- Extend `DecisionOption` with optional `tradeoffs`
- Extend `DecisionRequest` with `domain`, `context`, `includeRecommendations`
- Extend `DecisionResponse` with `decisionId`, `baseline`, `protege`, `human` fields
- Update Zod schemas

### Phase 3: Decision Storage
- Create `DecisionStore` class for in-memory storage
- Store decision records for outcome correlation
- Implement retrieval by decisionId

### Phase 4: Tool Enhancement
- Update `request-decision.ts` to handle new parameters
- Return enhanced response when `includeRecommendations: true`
- Generate and store `decisionId`

### Phase 5: New Tools
- Implement `get_decision_outcome` tool
- Implement `report_decision_result` tool
- Register new tools in plugin

### Phase 6: Testing
- Unit tests for new schemas
- Integration tests for enhanced decision flow
- Backward compatibility tests

## API Surface Changes

### Enhanced request_decision Parameters

```typescript
// New optional parameters (all backward compatible)
interface RequestDecisionParams {
  question: string;           // Existing
  options: DecisionOption[];  // Enhanced with tradeoffs
  context?: string;           // Existing (repurposed)
  urgency?: Urgency;          // Existing
  timeout?: number;           // Existing

  // NEW optional parameters
  domain?: string[];          // For principle matching
  decisionContext?: {         // Structured context
    projectConstraints?: string[];
    relatedIssue?: string;
    [key: string]: unknown;
  };
  includeRecommendations?: boolean; // Get three-layer back
}
```

### Enhanced DecisionResponse

```typescript
interface DecisionResponse {
  requestId: string;          // Existing
  type: 'selection';          // Existing
  selectedOption: string;     // Existing
  respondedAt: Date;          // Existing

  // NEW fields
  decisionId: string;         // For outcome reporting

  // Only present if includeRecommendations was true
  baseline?: Recommendation;
  protege?: ProtegeRecommendation;
  human?: HumanDecision;
}
```
