# Clarifications

Questions and answers to clarify the feature specification.

## Batch 1 - 2026-01-19 18:23

### Q1: Recommendation Computation
**Context**: The spec shows baseline and protégé recommendations in the response, but it's unclear who computes them. This affects architecture significantly - whether the plugin needs AI/ML logic or just passes through external data.
**Question**: Is the humancy plugin responsible for computing baseline and protégé recommendations, or does it receive these from an external service (e.g., a protégé service)?
**Options**:
- A: Plugin computes recommendations internally (needs AI/ML integration)
- B: Plugin receives recommendations from external service and passes through
- C: Stub/mock recommendations for now, actual computation deferred

**Answer**: **Option B** - Plugin receives recommendations from external services and passes through.

The architecture clearly separates concerns:
- **Baseline** comes from "consulting agents" collaborating (Layer 1)
- **Protégé recommendation** comes from a trained AI that applies the human's learned wisdom (Layer 2)

The plugin should be a **pass-through/orchestration layer** that receives pre-computed recommendations, not an AI/ML system itself.

### Q2: get_decision_outcome Tool
**Context**: The New Tools table lists `get_decision_outcome` for checking previous decision outcomes, but there's no example or detailed description. This affects the API surface.
**Question**: What should `get_decision_outcome` return? Is it for checking if a decision was made (status), or retrieving the full decision history including outcome reports?

**Answer**: Return the full decision record including outcome data when available.

Based on the `DecisionRecord` interface in the decision framework, return:
- The original decision context and three-layer breakdown (baseline, protégé, human)
- The outcome if reported (`measuredAt`, `quality`, `notes`)
- Status indicating whether outcome has been reported yet

This supports the attribution and learning loops described in the architecture.

### Q3: Backward Compatibility Approach
**Context**: The spec mentions both enhancing `request_decision` with optional parameters AND creating a new `request_decision_v2` tool. This is redundant - need clarity on the approach.
**Question**: Should we (A) enhance the existing `request_decision` with optional three-layer parameters, (B) create a separate `request_decision_v2` for the new features, or (C) do both?
**Options**:
- A: Enhance existing request_decision only (simpler, but mixes old/new)
- B: Create request_decision_v2 only (cleaner separation, deprecate old)
- C: Both - enhance request_decision AND add v2 (most flexible)

**Answer**: **Option A** - Enhance the existing `request_decision` only.

Rationale:
- Adding optional parameters (`domain`, `context`, `includeRecommendations`) maintains backward compatibility
- Creating a v2 is redundant if all new fields are optional
- Simpler API surface - one tool that grows rather than parallel tools
- The three-layer response only appears when `includeRecommendations: true` is set

### Q5: Decision ID Source
**Context**: The `report_decision_result` tool requires a `decisionId`, but the spec doesn't show where this ID comes from. This is needed for implementation.
**Question**: Where does the `decisionId` come from - is it returned in the original decision response, or generated by the calling agent?

**Answer**: The `decisionId` is generated by the humancy service and **returned in the original decision response**.

Per the decision framework:
```typescript
interface DecisionResponse {
  decisionId: string;  // Generated when decision is recorded
  ...
}
```

The caller receives this ID when making a decision and uses it later to call `report_decision_result`.
