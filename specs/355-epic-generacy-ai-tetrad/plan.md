# Implementation Plan: /cockpit:merge command

**Feature**: `/cockpit:merge` slash command that calls the `generacy cockpit merge` CLI, spawns a fixer subagent on red checks, re-evaluates, and never merges on red
**Branch**: `355-epic-generacy-ai-tetrad`
**Date**: 2026-06-26
**Spec**: [spec.md](./spec.md)
**Status**: Complete

## Summary

Ship one new file — `packages/claude-plugin-cockpit/commands/merge.md` — that defines the `/cockpit:merge` slash command. The command takes an issue/epic reference (resolved via the shared resolver from #788) plus an optional `--no-fix` flag and an optional `--max-fix-attempts=N` flag (default `1`). It invokes the `generacy cockpit merge` CLI verb (#789) which returns a structured JSON result indicating either `merged`, `red` with a typed `reason`, or another non-mergeable state. On `reason: checks-failing` or merge conflicts, the command spawns a `cockpit-fixer` subagent via the Task/Agent tool, then re-invokes the (idempotent) CLI verb to re-evaluate — up to `max-fix-attempts` times. All other non-mergeable states (`missing-label`, `pending` checks, `draft`, missing approval) terminate the command with an actionable terse report.

No new TypeScript, no new tests, no MCP coupling — this is a single markdown slash-command file that delegates to the existing CLI verb and the existing Task/Agent tool. Sibling assumptions (the resolver in #788, the fixer subagent definition, the CLI verb's JSON contract in #789) are *consumed*, not authored here.

## Implementation Phases

### Phase 0: Verify the contracts we depend on

Before writing any markdown, confirm or surface gaps in:

1. **#788 (resolver)**: confirm there's a documented invocation pattern for "resolve issue/epic ref → PR number / repo / ref." If the resolver is not yet landed, write `merge.md` to a *named* contract (referenced in `contracts/`) and flag the dependency.
2. **#789 (CLI verb)**: confirm the JSON output shape — at minimum `{ result, reason }` with the `reason` enum including `checks-failing`, `merge-conflict`, `missing-label`, `pending`, `draft`, `missing-approval`. If undocumented, codify the assumed shape in `contracts/merge-cli.contract.md` and treat any divergence at integration time as a sibling bug, not a `merge.md` bug.
3. **Fixer subagent**: confirm whether a named `cockpit-fixer` subagent exists. If only a "general agent with a fixer prompt" pattern exists (clarification Q1 allowed either), pick the named subagent if present and fall back to the inline-prompted general agent otherwise — document the choice in `research.md`.

### Phase 1: Author `merge.md`

1. Write frontmatter: `description`, positional `arguments.ref` (required), flags `--no-fix` and `--max-fix-attempts=N`.
2. Write the prompt body following the structure of sibling commands in `packages/claude-plugin-agency-spec-kit/commands/`:
   - **Parse arguments** — resolve `ref` via the #788 resolver; default `--max-fix-attempts` to `1`.
   - **Invoke CLI** — call `generacy cockpit merge <resolved-pr-ref>` via Bash; parse the JSON result.
   - **Decision tree** (matches clarification Q3):
     - `result: "merged"` → report success, exit.
     - `result: "red"` with `reason ∈ { "checks-failing", "merge-conflict" }`:
       - If `--no-fix` → report `red`, the `reason`, and the failing checks; exit. **Do not merge.**
       - Otherwise, increment attempt counter; if `attempts > max-fix-attempts`, report `red`, the final `reason`, and the trail of attempts; exit. **Do not merge.**
       - Otherwise, spawn the `cockpit-fixer` subagent via Task with the failing-check payload as context; on subagent return, loop back to "Invoke CLI."
     - `result: "blocked"` with `reason ∈ { "missing-label", "missing-approval", "draft", "pending" }` → report the `reason`, the actionable next step, and exit. **Do not spawn the fixer.** (Per Q3: `pending` checks are handled by `cockpit:watch`'s roll-up.)
     - Any unrecognized `result` or `reason` → terse error, exit.
3. Output discipline: terse status lines only; no chatty summaries.

### Phase 2: Validate

4. JSON-shape check: write down (in `contracts/merge-cli.contract.md`) the exact shapes the command depends on; any drift surfaces as an integration bug at runtime.
5. Manual install + smoke test: install the plugin in a Claude Code environment, run `/cockpit:merge <ref>` against:
   - a green-approved PR (expect `merged`),
   - a red PR with the fixer enabled (expect fixer spawn + re-eval),
   - a red PR with `--no-fix` (expect terse red report, no fixer),
   - a pending-checks PR (expect stop + actionable report, no fixer),
   - a draft / missing-approval PR (expect stop + actionable report).
6. Confirm the file lives only at `packages/claude-plugin-cockpit/commands/merge.md` and that no other file in the repo was modified (isolation check).

## Open Risks

| Risk | Mitigation |
|------|------------|
| #789's JSON contract has not been finalized when `merge.md` ships | Codify the assumed shape in `contracts/merge-cli.contract.md`. At integration time, the contract is the agreement; any divergence is a sibling-issue bug, surfaced back to the user. |
| `cockpit-fixer` subagent does not yet exist | Inline fallback per clarification Q1 — spawn a general agent with an embedded fixer prompt that takes the failing-check JSON as input. Document the fallback in `research.md` so it can be swapped to the named subagent later without changing this command's external behavior. |
| Resolver (#788) is unavailable | Without the resolver, the command cannot accept arbitrary issue/epic refs. Surface this as a hard blocker — clarification Q4 explicitly rejected "operate on current branch." Do not ship a `current-branch` fallback. |
| Fixer loops indefinitely or runs up cost | Hard cap via `--max-fix-attempts` (default `1`, per Q5). Each attempt MUST log the attempt number; exiting on cap MUST report the trail. |
| User passes `--no-fix` expecting a dry-run that still merges on green | `--no-fix` only suppresses the fixer; green PRs still merge. Document this explicitly in the command's frontmatter `description` and in `quickstart.md`. |
| Race: PR transitions from `pending` to `red` between CLI calls | Acceptable. The CLI's idempotent re-eval (Q2) catches it on the next loop iteration; `pending` itself stops the command (Q3) so the race is bounded to a single CLI invocation. |
