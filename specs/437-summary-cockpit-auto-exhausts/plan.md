# Implementation Plan: `/cockpit:auto` dispatches off enriched doorbell line, drops per-event `cockpit_status` re-check for label-driven classes

**Feature**: Teach the `/cockpit:auto` skill to parse the NDJSON doorbell line the engine now emits (`{ type, repo, kind, number, event, to, labels, url, checks? }`) and dispatch off `to`/`labels` directly for label-driven classes (D.1–D.4, D.7, D.9, D.9a–D.9d), consulting the baked-in `checks` verdict for D.5/D.6. Removes the dominant GraphQL rate-limit consumer — the per-event `cockpit_status(epic, json=true)` re-check that fans out ~28 GraphQL calls each — while retaining the re-check for D.8, D.10, and D.11 (human/consequential gates).
**Branch**: `437-summary-cockpit-auto-exhausts`
**Issue**: [#437](https://github.com/generacy-ai/agency/issues/437)
**Date**: 2026-07-17
**Status**: Complete

## Summary

`/cockpit:auto` exhausts the GitHub GraphQL rate limit (5000 pts/hr) despite low event volume because `auto.md` step 4a re-checks live state via `cockpit_status(epic, json=true)` for **every** actionable event in the drained batch. That call fans out ~28 GraphQL calls for a mid-size epic; a 3-event wake is ≈ ~95 calls. Post-generacy#985 the doorbell line the parent gets on every wake carries the exact fields it was querying for (`to`, `labels`, and a baked `checks` verdict for merge-gate events), so the re-check is redundant for label-driven classes. This spec teaches the skill to read the line.

The change is scoped to two files in this repo, both under `packages/claude-plugin-cockpit/`:

1. **`commands/auto.md`** — dispatch prose edits (step 4a contract, D.1–D.7 dispatch rows, D.9/D.9a–d ledger-only rows, D.5/D.6 checks-verdict path, invariant §7 wording, ledger action+outcome vocabulary).
2. **`tests/playbook-verification.test.ts`** — re-pin the existing playbook-verification assertions to the new dispatch shape. Per the CLAUDE.md rule, weakening or deleting a pin is not the correct response; the pin gets re-authored to match the new contract in this same PR.

The engine side (content-ful `lineForEvent` + local `to`-classification + baked `checks` verdict) is a companion change in **generacy-ai/generacy#985**. Per the one-issue-per-repo rule the two land in lockstep. This PR's skill-side edits carry a graceful-degradation gate (per Q2=B) so that on older engines (or content-less doorbell modes), the skill falls back to today's re-query behaviour without runtime error — the enriched-vs-bare gate is `JSON.parse` success AND the parsed object carries both `to` and `labels`. Missing either treats the line as bare.

The load-bearing rewrites inside `auto.md`:

- **Step 4a (§ Main loop, per-event iteration)** — reframed as a single "resolve authoritative state" step whose implementation is "prefer the enriched line's `to`/`labels`/`checks`; fall back to one `cockpit_status`/`cockpit_merge` query on absence" (Q3=B). Removes the current "The batch event is advisory; the live return is authoritative" invariant for label-driven classes; retains it for the merge-gate fallback and D.8/D.10/D.11 paths.
- **D.1–D.4, D.7, D.9, D.9a–D.9d dispatch rows** — the "call `cockpit_status(...)` for actionable dispatch classes (D.1–D.8, D.10, D.11)" fragment in step 4a becomes "call `cockpit_status(...)` for D.8, D.10, D.11 only." The D.9-family rows remain ledger-only (invariant §8 unchanged). The D.1–D.7 rows drop the "The parent **always** re-checks live state" preamble and are re-narrated to read `to`/`labels` from the enriched line.
- **D.5 / D.6 (merge gate)** — consult the line's `checks` field; if `green`, D.5 branch (call `cockpit_merge`); if `red`, D.6 branch (bounded fixer subagent); if the field is **absent** or its value is `pending`, fall back to a single authoritative `cockpit_status` / `cockpit_merge` query (Q4=B: defer-on-pending was rejected because smee doorbell delivery is best-effort and a lost follow-up event would silently stall the merge; the extra query cost is ≈once per issue).
- **Invariant §7 ("Stream consumption is unfiltered")** — the mandate at auto.md:53 (currently: *"The stdout content is a doorbell only: the parent NEVER parses lines for content."*) is **removed and rewritten** to state that (a) enriched lines are parsed as NDJSON per the § Enriched-line dispatch contract, (b) `cockpit_await_events` remains the sole source of typed batches for the merge-gate fallback and the D.8/D.10/D.11 paths, and (c) content-based filters that could silently drop events remain prohibited (the anti-drop protection of §7 stays; the "never parse" mandate is what changes). The invariant number stays §7.
- **§ Ledger action+outcome vocabulary** — every ledger row emitted from the label-driven dispatch path (D.1–D.4, D.7, D.9, D.9a–D.9d) grows a `source: enriched-line` suffix column when the dispatch was driven by an enriched line, and no suffix (equivalent to `source: re-query`) when the dispatch was driven by the fallback `cockpit_status` path. Post-mortems `grep`ing on `source: enriched-line` distinguish the two paths without needing an extra column in every table.

## Technical Context

- **Language / runtime**: The playbook is a Claude Code plugin markdown file (`packages/claude-plugin-cockpit/commands/auto.md`) interpreted by the harness at invocation time. No compiled code; the "implementation" is prose the model executes tool-by-tool. The test that pins the prose is `packages/claude-plugin-cockpit/tests/playbook-verification.test.ts` — a Vitest suite that greps the markdown for load-bearing strings.
- **Framework**: Claude Code harness (unchanged). Load-bearing tools this fix touches by prose: harness `Monitor` (already spawns the doorbell sensor in step 2 — the change is that its stdout is now read as NDJSON instead of treated as an opaque doorbell), the seven `cockpit_*` MCP tools bound in step 3 (unchanged — the change is that `cockpit_status` is called *less often*).
- **External CLI dependency**: `generacy cockpit doorbell <epic-ref>` — the engine-owned subprocess whose stdout format is the contract that lands via generacy#985. This PR's skill-side reader parses that format; the format itself is defined and versioned in the generacy repo.
- **Cross-repo dependency**: `generacy-ai/generacy#985` is the companion PR that makes the doorbell line content-ful (adds `to`/`labels`/`checks` to `lineForEvent`, wires local `to`-classification, bakes the `checks` verdict). This PR does NOT hard-fail if generacy#985 isn't deployed on a cluster — the enriched-vs-bare gate falls back to today's re-query behaviour for any bare or malformed line (FR-005 graceful degradation, Q2=B). The two are designed for lockstep landing, but a delayed generacy-side rollout leaves the skill functional (at pre-#437 cost) rather than broken.
- **Constraint (Q1=A)**: Dispatch-class scope — the enriched-line dispatch path covers D.1 (clarification), D.2–D.4 (reviews / manual-validation), D.7 (error/failed), D.9 (address-pr-feedback), D.9a (pr-feedback), D.9b (children-complete), D.9c (dependencies), D.9d (phase:\*). D.5/D.6 (merge gate) uses the baked `checks` verdict with a defined fallback per Q4. D.8 (phase-complete), D.10 (unrecognized), and D.11 (merge-conflicts) retain the per-event `cockpit_status` re-check because they open human/consequential gates where a stale-line dispatch could open a gate against superseded state, and they are all low-frequency.
- **Constraint (Q2=B)**: Enriched-vs-bare detection heuristic — a line is treated as enriched iff it JSON-parses to an object AND carries both `to` and `labels` fields. Missing either treats the line as bare and falls back to today's re-query. `checks` presence is NOT part of the enriched-vs-bare gate — a legitimate label-change line has no `checks` — it is handled inside the D.5/D.6 path per FR-003.
- **Constraint (Q3=B)**: Step-4a "live is authoritative" contract — the step stays as a single "resolve authoritative state" contract; the implementation phrase is "prefer the enriched line; fall back to one `cockpit_status` on absence." One unified source-of-truth priority covers both label-driven and merge-gate paths, and folds FR-005 graceful degradation in naturally.
- **Constraint (Q4=B)**: `checks: pending` handling for D.5/D.6 — treat `pending` identically to "verdict absent": one authoritative `cockpit_status`/`cockpit_merge` query. Defer-on-pending (option A) was rejected because smee doorbell delivery is best-effort/lossy; a lost follow-up event could silently stall the merge, a real correctness hazard. Merge-gate dispatch is ≈once per issue, so the extra query cost is negligible.
- **Constraint (Q5=C)**: Ledger row source-of-truth — the row reflects the doorbell line as-received (no extra `cockpit_status` read for ledger purposes), plus a `source: enriched-line` marker distinguishing enriched-line dispatch from fallback re-query rows. Option B (fresh live-state read for the ledger) was rejected in-context per FR-002 intent — it would negate the SC-001 saving.
- **Constraint (playbook-verification pin rule, from CLAUDE.md)**: The existing `playbook-verification.test.ts` block that pins step 4a's current "The batch event is advisory; the live return is authoritative" invariant will fail on this PR by design. The correct response is to **re-pin the assertion to the new contract** in this same PR — do not weaken or delete an assertion to make the test pass. The negative-pin rule (from #433) applies transitively — a positive + negative pin catches partial reverts.

- **§4 No cross-slash-command invocation** — unchanged.
- **§5 Analysis in subagents** — unchanged (the enriched-line parse is not analysis; it is transport).
- **§6 Autonomy policy out of scope** — unchanged (no new auto-approve; the human gates that fire are unchanged).
- **§7 Stream consumption is unfiltered** — **shifts**. This is the one norm-shift this PR makes. Content-based filters over the stream are prohibited."* The post-#437 wording keeps the anti-drop protection (no content-based filter that could silently drop legitimate events) but drops the "never parse" clause and states that enriched lines ARE parsed per the § Enriched-line dispatch contract. `cockpit_await_events` remains the sole source of typed batches for the merge-gate fallback and D.8/D.10/D.11 paths — that is where "authoritative" now lives, per Q3=B.
- **§8 Ledger-only rows are cheap by contract** — **strengthens**. D.9 / D.9a–D.9d were already ledger-only (no `cockpit_status` re-check); this PR extends the cost contract implicitly to D.1–D.4 and D.7 (the frequent classes that carried ≈all the load): those rows now also add no `cockpit_status` re-check on the enriched-line path. Playbook edits that reintroduce a per-event re-check on the enriched-line path for these classes are efficiency regressions.
- **§9 MCP-tool-only invariant** — unchanged. The enriched-line parse is a Bash-free read of `Monitor`'s stdout line; the migrated verbs (`status`, `context`, `queue`, `advance`, `resume`, `merge`) continue to be invoked exclusively via `cockpit_*` MCP tools when the fallback path fires.

**Complexity Tracking** — one norm-shift (§7) requires explanation. The pre-#437 mandate exists because pre-#985 the doorbell line carried at most a bare event type; parsing it for dispatch inputs would have meant guessing at fields the line didn't carry, silently producing a wrong dispatch. Post-#985 the line carries the fields authoritatively (engine-classified, matched to what `cockpit_status` would return), so parsing IS the correct dispatch input. The anti-drop protection of §7 (no content-based filter that silently drops legitimate events) is retained; only the "opaque doorbell" premise is retired, and only because the premise no longer matches the transport layer's shape.

## Key Technical Decisions

Full rationale in `research.md`.

1. **Dispatch-class scope: convert D.9a–D.9d alongside D.9; retain re-check for D.8, D.10, D.11** (Q1=A). The frequent classes (D.1–D.4, D.7, D.9, D.9a–D.9d) carry essentially all the load — a mid-size epic hits these on every state transition; a 3-event wake fans out ≈95 GraphQL calls with the current re-check. Converting these drops the per-event cost to zero GraphQL calls for the enriched-line path. D.8 (`phase-complete`), D.10 (unrecognized), and D.11 (`merge-conflicts`) open human/consequential gates where a stale-line dispatch could open a gate against superseded state; they are all low-frequency (phase-complete ≈once per phase; D.10/D.11 are error/escalation cases), so retaining the authoritative re-check costs almost nothing while removing the stale-state risk.
2. **Enriched-vs-bare detection: JSON.parse to object AND `to` + `labels` present** (Q2=B). Option C (additionally require `checks`) was rejected because a legitimate label-change line has no `checks` — C would wrongly route every label-driven line to full re-query. Option A (JSON-parse success only) was rejected because a partial payload (parses as JSON but missing `to`) would be acted on with incomplete inputs. `checks` presence/absence is handled separately in the D.5/D.6 path per FR-003, not in the enriched-vs-bare gate.
3. **Step-4a "authoritative state" framing: keep step 4a as a single unified contract** (Q3=B). The step stays as "resolve authoritative state" whose implementation is "prefer the enriched line when present; fall back to one `cockpit_status` on absence." This unifies label-driven and merge-gate paths under one source-of-truth priority, is easier to narrate, easier to pin in playbook-verification, and folds FR-005 graceful degradation in naturally. Framing (i) (drop step 4a for label-driven classes; re-scope the invariant to merge-gate fallback only) is more surgical but harder to explain and creates two divergent narration paths for one dispatch loop.
4. **`checks: pending` handling: treat like "verdict absent" — fall back to one authoritative query** (Q4=B). Defer-on-pending (option A) minimizes queries but relies on the follow-up doorbell event arriving. smee doorbell delivery is best-effort/lossy — a lost follow-up event would silently stall the merge, a real correctness hazard. Merge-gate dispatch is ≈once per issue, so the extra query cost is negligible; treating `pending` as "not decisive" is consistent with FR-003's "fall back when not decisive" wording.
5. **Ledger row source-of-truth: doorbell line as-received + `source: enriched-line` marker column** (Q5=C). Option B (fresh live-state read for the ledger only) was rejected in-context per FR-002 intent — it would negate the SC-001 saving. Option A (line as-received, no marker) is cheaper and reproducible but loses the audit trail for post-mortems distinguishing enriched-line rows from fallback re-query rows. Option C is the audit-friendly middle ground: the marker is exactly what post-mortems need to validate that engine classification matches GitHub reality while the new path beds in.
6. **Invariant §7 rewrite (retain anti-drop, drop "never parse")**. The pre-#437 mandate mixed two guarantees: (a) no content-based filter that could silently drop legitimate events; (b) the doorbell line is opaque. Guarantee (a) is load-bearing and stays. Guarantee (b) is retired because the transport layer's shape changed (generacy#985 makes the line content-ful). Splitting the two guarantees in the rewritten §7 wording makes the retained anti-drop protection unambiguous — a future author reading only §7 sees "content-based filters that could silently drop legitimate events are prohibited" as a standalone rule, without the confusing "never parse" clause it used to be bundled with.
7. **Playbook-verification test edits: re-pin, do not weaken** (CLAUDE.md invariant). The two existing pins that assert the pre-#437 wording (`playbook-verification.test.ts` block that asserts step 4a's advisory-vs-authoritative wording; block that asserts D.1–D.7 dispatches call `cockpit_status`) are re-authored in this PR to pin the new contract. Positive + negative pin per the #433 pattern: positive asserts the new wording is present; negative asserts the old wording is gone. New pins for §7 wording, ledger `source: enriched-line` marker vocabulary, D.5/D.6 fallback rule, and D.8/D.10/D.11 retain-the-re-check add to the pin surface without weakening any existing assertion.

## Constraints and Assumptions

- **generacy#985 is the source of truth for the NDJSON line schema** (`{ type, repo, kind, number, event, to, labels, url, checks? }`). This PR's parser reads the fields the engine emits; it does not define them. Changes to the schema on the engine side are versioned in the generacy repo. A schema drift (engine changes a field name, this PR's parser doesn't update) surfaces as the enriched-vs-bare gate failing (missing `to` or `labels`) and falling back to the re-query path — a graceful degradation, not a runtime error.
- **Load-bearing sole source for typed batches**: `cockpit_await_events` remains the sole source of typed batches for D.8 (phase-queue gate scope computation), D.10 (unrecognized state — the escalation gate needs authoritative state), D.11 (merge-conflicts — same), and the merge-gate fallback path (D.5/D.6 on absent or `pending` verdict). This is preserved to keep the anti-drop protection of invariant §7 (no content-based filter that silently drops legitimate events) — the enriched line is a dispatch input for label-driven classes, but `cockpit_await_events` is still the canonical typed-batch source for the escalation surfaces.
- **Backwards compatibility**: A cluster running an older `generacy` (pre-#985, no enriched line) sees every doorbell line fail the enriched-vs-bare gate (missing `to` and/or `labels`) and falls back to today's `cockpit_status` re-check per FR-005. The pre-#437 behaviour is preserved verbatim on the fallback path; no regression for older engines.
- **Merge-gate correctness under `pending`**: The Q4=B decision (fall back to one authoritative query on `pending`) is a correctness/cost tradeoff. The cost is bounded — merge-gate dispatch is ≈once per issue over the epic's lifetime, so an extra `cockpit_status` per `pending` event is a rounding error against the ≈95-GraphQL-per-wake savings this PR delivers. The correctness win is that a lost follow-up doorbell event cannot silently stall the merge — a real risk since smee is best-effort delivery.
- **Session-local mute set and dispatched-issues set semantics preserved**: The enriched-line dispatch path still checks the session mute set and (for D.11) the dispatched-issues set before writing a ledger line. Muting and dedup semantics are orthogonal to the dispatch source; the mute-set / dedup checks live above the dispatch decision in step 4b (per current auto.md § D.11 step 1, `auto.md:446`).
- **Ledger dual-write rule preserved**: Every dispatched event still writes exactly one ledger line (transcript print + append to the persistent `.ledger` file). The `source: enriched-line` marker is a suffix column in the outcome slot; it does not add or remove ledger lines. The mandatory-per-dispatch rule from `auto.md § Ledger` (`A dispatch without a ledger line is a protocol violation`) is unchanged.

## Out of Scope

- **Engine-side `lineForEvent` implementation** — owned by generacy#985. This PR does not define the field names or JSON schema of the doorbell line; the parser here reads whatever the engine emits and gracefully degrades on missing fields.
- **`cockpit_await_events` changes** — the tool's contract is unchanged. This PR reduces how often it fires (fewer `cockpit_status` calls per wake) but does not change its parameters, return shape, or error taxonomy.
- **Retiring `cockpit_await_events`** — even though the enriched line now carries dispatch-sufficient state for label-driven classes, `cockpit_await_events` remains the sole source of typed batches for D.8, D.10, D.11 escalation gates and the merge-gate fallback path. Retiring it would collapse the typed-batch abstraction and require replicating the batch-coalesce / cursor / recovery machinery in the enriched-line parser. Not in scope.
- **Retiring the C4 heartbeat lifecycle** — the 5-minute `ScheduleWakeup` heartbeat remains the belt-and-braces recovery signal when `Monitor` is silent, and its ledger accounting (`heartbeat · schedule-wakeup · fired · drain empty|complete`) is unchanged. The enriched line reduces per-wake cost; it does not remove the need for a periodic wake.
- **Add-existing / file-new intent flows** — the mid-run scope mutation paths (add-existing, G.6 filing gate) are operator-typed, not doorbell-driven, and are untouched by this PR.
- **The `openAdHocIssues` helper for D.8** — this helper (added by #416) still needs `cockpit_status` per-ad-hoc-ref to compute open-ad-hoc counts for the phase-queue gate presentation. That is intentional and out of scope for this PR: D.8 is one of the three retain-the-re-check classes; a stale open-ad-hoc list at the phase-queue gate could silently silence "hold" recommendations against superseded state.
- **A retry / cancel primitive for the outstanding `ScheduleWakeup` heartbeat** — the harness does not expose a cancel primitive today; the pre-#437 semantics (stale heartbeats fire harmlessly, drain returns zero events, one extra ledger line) are preserved. Not in scope.
