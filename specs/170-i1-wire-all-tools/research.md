# Research: I1: Wire all tools into plugin.ts

**Feature**: `170-i1-wire-all-tools`
**Date**: 2026-02-01

## Technology Decisions

### 1. Tool Registration Pattern

**Decision**: Factory function pattern with `createTools()` aggregator

**Rationale**:
- Each tool is created by a factory function (e.g., `createGitOpsTool()`)
- The `createTools()` function orchestrates creation of all tools
- This allows for dependency injection (config, coreAPI, providers)
- Tools can be created individually for testing

**Alternatives Considered**:
- Class-based tools with decorator registration (more boilerplate)
- Singleton tools (less flexible for configuration)
- Dynamic tool loading (more complex, harder to type)

### 2. Provider Registry Pattern

**Decision**: Lazy instantiation with caching via `ProviderRegistry` class

**Rationale**:
- Providers are only created when first accessed
- Cached instances prevent repeated initialization
- Factory pattern allows for provider-specific configuration
- Clean separation between provider types

**Implementation**:
```typescript
// Registry stores factories and caches instances
const providerFactories = new Map<BacklogProviderName, ProviderFactory>();
const providers = new Map<BacklogProviderName, BacklogProvider>();

// Lazy instantiation on first access
getProvider(name) {
  if (!providers.has(name)) {
    const factory = providerFactories.get(name);
    providers.set(name, factory(config));
  }
  return providers.get(name);
}
```

### 3. Humancy Integration

**Decision**: Optional integration via `coreAPI.getTool()`

**Rationale**:
- Humancy plugin may not always be loaded
- Graceful degradation when not available
- Questions still written to clarifications.md even without Humancy
- Future-proof for alternative human input channels

**Implementation**:
```typescript
// Check if Humancy is available
const askQuestion = coreAPI.getTool?.('humancy.ask_question');
if (!askQuestion) {
  return { sent: false, error: 'Humancy plugin not available' };
}
```

### 4. Configuration Schema

**Decision**: Zod-based schema with defaults

**Rationale**:
- Runtime validation with TypeScript type inference
- Sensible defaults for all settings
- Backwards compatibility with legacy config format
- Clear error messages for invalid configuration
