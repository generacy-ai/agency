## Summary

Close the finding #62 misdiagnosis observed on the cockpit v1.5 auto-mode integration smoke test (generacy-ai/tetrad-development#92) on snappoll-1 run 11. On a repeat D.7 failure (Requeue → `failed:validate` again within ~90s), the auto session **never fetched the new failure evidence** — the parent asserted similarity to the prior failure ("requeue failed identically") and dispatched on the assertion. Both diagnosis subagents returned Skip verdicts built on that unverified premise. Ground truth (from the fresh #915 reason-bearing alerts): the failures had **changed class entirely** — the requeue had *worked* (the #914 base-merge brought the scaffold in and `npm ci` passed), and the new failures were two distinct in-branch defects (#3: `@prisma/client` missing from the epic's dependency plan; #4: a source-guard test tripped by the implementation's own doc comment). "Needs out-of-band branch sync" was wrong for both; the verdicts, their confidence labels, and the escalation-gate presentation were all built on an unverified premise. Cost: the operator was steered toward Skip (which would have wedged P1 and the epic) when the actual remedies were a one-line dependency addition and a comment reword.

Root cause: `auto.md` D.7's evidence contract covers the **first** dispatch (parent fetches the engine bundle via `cockpit_context` → spawns diagnosis subagent with alert-body payload) but is silent on the **repeat-failure** path. The session's continuation pattern (SendMessage to the existing subagent) is architecturally correct — context reuse is exactly right — but the continuation prompt carried the parent's *conclusion* ("identical") instead of *evidence*. Similarity between two failures is a determination only evidence can support: the engine now ships classifier reasons and output tails in every alert (#915) precisely so this comparison never has to be guessed. The parent-authored summary of evidence violates the loop-trust-boundary principle at a new surface (previously enforced at engine-to-parent and parent-to-subagent boundaries; now extended to parent-to-continuing-subagent).

Three edits, applied in the same PR:

1. **Rewrite D.7 step 1 (evidence fetch) with a first-vs-repeat dispatch split.** The trigger classification (per-Q1=B: any second `agent:error` / `failed:*` on the same issue in one contiguous auto invocation is a repeat, regardless of subtype match; Stop → restart resets first-vs-repeat state) determines which sub-path runs:
   - **First dispatch** (issue's first `agent:error` / `failed:*` in this invocation): unchanged from today's D.7 step 1. Call `cockpit_context(issue=<issue-ref>)`; the engine bundle payload is the first-dispatch evidence.
   - **Repeat dispatch** (issue's second-and-subsequent `agent:error` / `failed:*` in this invocation): call `cockpit_context(issue=<issue-ref>)` again — same evidence verb as first-dispatch. **No dispatch of a repeat D.7 without the new alert body in hand.** The parent MUST NOT characterize the fresh failure with a phrase like "requeue failed identically" or "same as before"; the parent's role at this boundary is pure transport.

2. **Rewrite D.7 step 2 (subagent dispatch) with a repeat-continuation shape + return-schema addendum.** The parent's continuation prompt to the diagnosis subagent (either via SendMessage to an existing subagent or via fresh spawn on continuation-miss per Q4=A) contains:
   - **Prior-context reference or verbatim prior alert body** — SendMessage form: prior-context reference ("continuing from earlier diagnosis"); fresh-spawn form (subagent already returned / disposed): verbatim prior alert body from `cockpit_context` return payload (the prior alert is a persistent engine-marked comment on the issue — never lost).
   - **Verbatim new alert body** — the fresh `cockpit_context` return payload's failure-alert comment body (classifier reason, error taxonomy, failing test/step, output tail). No parent characterization.
   - **Verdict-return-schema addendum for repeat dispatches**: the JSON return payload's shape grows two required fields on repeat dispatches: `failure_class_changed: boolean` (per-Q2=B any-of-three rule — see below) and `failure_classes_seen: string[]` (per-Q3=D running list of failure classes observed across this issue's repeat dispatches in the current session). On first dispatch, both fields are absent (or explicitly `null`); on repeat dispatches, both are required.
   
   **`failure_class_changed` computation rule (Q2=B)**: the subagent computes `failure_class_changed = true` iff *any* of the following three dimensions differs between the fresh and immediately-prior alert:
   - **`classifier_reason`** — engine-authored (post-#915), compared by **exact string match** on the field's value. Absent-vs-present counts as differing by definition (an alert with no `classifier_reason` differs from an alert with one, even if the parent's own summary of "same" would say otherwise).
   - **`error_taxonomy`** — engine-authored (post-#915), compared by **exact string match**. Absent-vs-present differs.
   - **`failing_test/step`** — free-text from the CI log; the subagent derives a **canonical test identifier** (test-runner-agnostic `<file>::<name>` form for test failures; equivalent stable identifier for non-test failing steps) and compares by exact string match on the canonical form. This defends against line-number and duration drift across runs of the same failure (a rerun of the same failing test on a different line number would false-positive under raw comparison; canonicalization compares identity, not formatting). Absent-vs-present differs.
   
   **`failure_classes_seen` computation rule (Q3=D)**: on each repeat dispatch, the subagent takes the running list from the prior verdict's `failure_classes_seen` (or an empty list for the second dispatch), appends the fresh alert's classifier identifier (typically the `classifier_reason` value or, if absent, the canonical failing-test identifier), and returns the updated list. Rendered in the verdict text as "classes this session: `<class1>` → `<class2>` → `<class3>` …" so cycles like A → B → A are visible at gate time in one human-readable line.

3. **Extend G.4(b) presentation block (in § Gate contract) with a `failure_class_changed` row + `failure_classes_seen` line on repeat dispatches.** The existing five-element block (Agent error on `<issue-ref>` / Root cause / Evidence / Current state / Suggested decision + confidence) gains a sixth element between "Evidence" and "Current state":
   ```
   **Failure class changed since prior:** <yes | no>  (classes this session: <class1> → <class2> → …)
   ```
   This row appears only on repeat dispatches; on first dispatch, the row is absent (the field is `null`/undefined). The row is populated verbatim from the verdict — no in-parent re-analysis. The recommendation calculus at the gate should reflect that a changed class after a Requeue usually means the requeue *made progress* (this incident's Skip recommendations inverted it); the row surfaces that signal directly at the gate.

- **Trigger scope: per-issue, any failure class, per contiguous invocation** (Q1=B). A second `failed:*` on the same issue in one auto invocation is a repeat — regardless of subtype match; a `failed:validate` → `failed:implement` shift is itself high-signal evidence of movement and should trip the repeat sub-path. Session restart resets first-vs-repeat state (session mutes, cursors, sweep state are all session-local by established convention per #406 Q2's argument; a restart's startup sweep does a fresh first-dispatch with fresh evidence, which is safe by construction against this spec's failure mode). Q1=A (per-subtype) is rejected because it throws away prior context exactly when the story got interesting; Q1=C/D (across restarts) buy cross-restart memory at the cost of ledger-as-database reconstruction that the restart-is-fresh design deliberately avoids.
- **`failure_class_changed` computation: any-of-three, with canonical test identifier; absent-vs-present differs** (Q2=B). The subagent compares along three dimensions: `classifier_reason` (engine-authored, exact string match), `error_taxonomy` (engine-authored, exact string match), and `failing_test/step` (canonicalized to `<file>::<name>` or equivalent stable identifier — never raw line text; line numbers and durations drift across runs of the same failure, canonicalization compares identity, not formatting). Any single dimension differing yields `true`. Absent-vs-present counts as differing by definition (an alert with no `classifier_reason` field differs from an alert with one). Q2=A (any-of-three, raw failing-step text) is rejected because raw text drifts across runs of the same failure, manufacturing false "changed" verdicts. Q2=C (all-of-three-must-differ) is rejected because a single-dimension shift is usually the signal, not noise. Q2=D (classifier reason alone) is rejected because the motivating incident's two failures were both process-level failures (exit 1) — #915 deliberately gives process paths no classifier reason — so under Q2=D `failure_class_changed` evaluates over two absent fields and misses the exact change this field exists to expose.
- **Comparison basis for third-and-subsequent dispatches: immediately-prior + running list of classes in verdict text** (Q3=D). The subagent compares fresh evidence against the *immediately-prior* failure only (not the original first-dispatch failure). `failure_class_changed` answers "did the last Requeue change anything?" — the per-decision question the operator is deciding on. Cycles like A → B → A are real, and the `failure_classes_seen` running list ("classes this session: npm-ci-EUSAGE → prisma-missing → npm-ci-EUSAGE") tells that story in one human-readable line, which is strictly clearer than two-boolean encodings (Q3=C rejected). One schema field with per-decision semantics, history as evidence text.
- **Continuation vs fresh spawn: fresh spawn with both alert bodies verbatim on continuation-miss** (Q4=A). When the first-dispatch subagent is no longer active (returned / disposed across a several-minute Requeue window), the parent spawns a fresh diagnosis subagent whose prompt contains both the fresh alert body AND the prior alert body verbatim — no parent characterization added. The prior alert is a persistent engine-marked comment on the issue (mechanically identifiable as the previous failure-alert comment); the parent's job on continuation-miss is pure transport. Q4=B (`failure_class_changed = null` when no baseline available) is rejected because it declares unavailable what's sitting on the issue in plain sight. Q4=C (parent MUST keep the first-dispatch subagent alive across the Requeue window) is rejected because it legislates against harness reality (subagents return by design; several-minute Requeue windows guarantee continuation-miss). Q4=D (persist first-dispatch verdicts in the ledger; hand them to a fresh subagent as prior evidence) is rejected because it feeds prior *verdict* instead of prior *evidence* — conclusions in place of evidence is the exact sin this spec abolishes, plus it grows the ledger into a database.

## Complexity Tracking

No constitution violations to justify. The change is intentionally minimal (D.7 step 1 body rewrite + step 2 verdict-schema addendum + G.4(b) presentation-block sixth-element row + one new test describe block with two assertions + one minimal fixture) and matches the fix scope named in the spec (fresh evidence on repeat dispatch + no parent characterization + verdict-schema addition + regression coverage). The design explicitly rejects:

- **Per-subtype trigger scope** (Q1=A rejected). A `failed:validate` → `failed:build` on the same issue would be a fresh first-dispatch, throwing away the prior context exactly when the subtype shift is itself high-signal evidence of movement. The repeat rule's payload is "hand the subagent prior evidence and compute the delta" — informative whenever *any* prior failure exists on the issue, subtype match or not.
- **Across-restart trigger scope** (Q1=C/D rejected). Buys cross-restart memory at the cost of ledger-as-database reconstruction the restart-is-fresh design (#406 Q2) deliberately avoids. A restart's startup sweep does a fresh first-dispatch with fresh evidence, which is safe by construction against this spec's failure mode.
- **Raw-text failing-step comparison** (Q2=A rejected). Raw line text drifts across runs of the same failure (line numbers, durations, temp workspace paths), manufacturing false "changed" verdicts. Canonicalization to `<file>::<name>` compares identity, not formatting.
- **All-of-three-must-differ** (Q2=C rejected). Backwards — a single-dimension shift is usually the signal, not noise. Reserves `true` for the case that all three shift together, treating single-dimension shifts as "same class, different instance" — which is exactly the pre-fix behavior this fix abolishes.
- **Classifier reason alone as authoritative** (Q2=D rejected). Disqualified by the motivating incident itself: both of run 11's failures were process failures (exit 1) — #915 deliberately gives process paths no classifier reason — so under Q2=D `failure_class_changed` for npm-ci-EUSAGE → vitest-prisma-failure evaluates over two absent fields and misses the exact change this field exists to expose.
- **First-dispatch baseline comparison** (Q3=B rejected). Silent about the immediately-prior Requeue's effect — the per-decision question the operator is actually deciding on. An alternating A → B → A pattern would show "unchanged" under first-comparison, hiding the cycle.
- **Two-boolean encoding** (Q3=C rejected). `failure_class_changed_since_prior: bool` AND `failure_class_changed_since_first: bool` presented as two rows makes the operator do arithmetic at gate time (`since_first=false, since_prior=true` = …a cycle? every reader does that decoding). Fields for decisions, prose for context — one boolean with per-decision semantics + a running list in verdict text is strictly clearer.
- **`failure_class_changed = null` on continuation-miss** (Q4=B rejected). Declares baseline "unavailable" that's sitting on the issue in plain sight — failure alerts are persistent engine-marked comments; the parent's job on continuation-miss is pure transport, not baseline-loss.
- **Design-constraint that parent MUST keep subagent alive** (Q4=C rejected). Legislates against harness reality — subagents return by design; several-minute Requeue windows guarantee this case arises. Converts a routine condition into an abort.
- **Persist prior verdicts in ledger; hand them as prior evidence** (Q4=D rejected). Feeds prior *verdict* instead of prior *evidence* — conclusions in place of evidence is a diluted form of the exact sin this spec abolishes. Plus it grows the ledger into a database.
- **Expected-to-fail test as the negative fixture's flag** (Q5=A rejected). A suite with a permanently red member normalizes red; "the checker rejects the fixture" as a green assertion carries the same information with none of the noise. Settled at #402 and #408; nothing has changed.
- **Separate verification harness beside the existing suite** (Q5=B rejected). Builds a second harness — surface-count creep for no reader benefit.
- **Adding invariant §10 "Every repeat D.7 dispatch fetches fresh evidence before spawning"**. Rejected as scope creep. The rule already lives in D.7 step 1's revised text and the audit's assertion; a numbered invariant would be a belt-and-suspenders duplicate — same anti-pattern the #384–#408 arc rejected. If future drift shows the `## Invariants` surface is needed, that's a follow-up finding.
- **Editing D.11 to add an equivalent repeat-path rule**. Scope creep. D.11 (merge-conflicts) has its own diagnosis-subagent step but on a different semantic axis — per-conflict resolution, not per-failure-repeat comparison. If a future finding surfaces a needed rule for D.11, that's a separate spec.
- **Adding cross-references from sibling playbooks**. Scope creep. D.7 dispatch lives in `auto.md` only; sibling playbooks have no dispatch section. Adding cross-references would create surfaces that drift for no reader benefit.
- **Fusion-phrase regex in the audit** (per #402's Q3=B rejection applied here). Content-sniffing on prose. Dialect-pinned to today's wording; false-negatives on any future author's alternative phrasing. Structural assertions (sub-path anchors + field-name presence + G.4(b) row anchor + rule-statement structural check) are the discipline established by #398/#402/#408.

## Key Design Decisions (from clarifications)

| # | Decision | Source |
|---|----------|--------|
| D1 | **Trigger scope: per-issue, any failure class, per contiguous invocation.** A second `failed:*` on the same issue in one auto invocation is a repeat — regardless of subtype match. A `failed:validate` → `failed:implement` shift is high-signal evidence of movement and should trip the repeat sub-path. Session restart resets first-vs-repeat state (per #406 Q2's session-local convention); a restart's startup sweep does a fresh first-dispatch with fresh evidence, safe by construction against this fix's failure mode. Q1=A (per-subtype) throws away prior context exactly when the story got interesting. Q1=C/D (across restarts) buy cross-restart memory at the cost of ledger-as-database reconstruction the restart-is-fresh design deliberately avoids. | Q1=B |
| D2 | **`failure_class_changed` computation: any-of-three, with canonical test identifier; absent-vs-present differs.** The subagent compares three dimensions: `classifier_reason` (engine-authored, exact string match), `error_taxonomy` (engine-authored, exact string match), `failing_test/step` (canonicalized to `<file>::<name>` or equivalent stable identifier — never raw line text; canonicalization defends against line-number and duration drift). Any single dimension differing yields `true`. Absent-vs-present differs by definition. Q2=A (raw failing-step text) manufactures false "changed" verdicts on rerun of the same failure. Q2=C (all-of-three) reserves `true` for a rare case, treating single-dimension shifts as "same class, different instance" — the pre-fix behavior. Q2=D (classifier reason alone) is disqualified by the motivating incident (both failures were process failures with no classifier reason). | Q2=B |
| D3 | **Comparison basis for N-th dispatch (N ≥ 3): immediately-prior failure + running list of classes in verdict text.** `failure_class_changed` answers "did the last Requeue change anything?" — the per-decision question the operator decides on. The `failure_classes_seen` running list ("classes this session: `<class1>` → `<class2>` → `<class3>`") tells cycles A → B → A in one human-readable line. Q3=B (first-dispatch baseline) hides cycles behind "unchanged". Q3=C (two booleans) makes the operator decode `since_first=false, since_prior=true` at gate time. Fields for decisions, prose for context. | Q3=D |
| D4 | **Continuation-miss: fresh spawn with both alert bodies verbatim; no parent characterization added.** When the first-dispatch subagent is no longer active, the parent spawns a fresh diagnosis subagent whose prompt contains both alert bodies verbatim. The prior alert is a persistent engine-marked comment on the issue (mechanically identifiable) — never lost. The parent's job on continuation-miss is pure transport. Q4=B (`failure_class_changed = null`) declares unavailable what's sitting on the issue in plain sight. Q4=C (subagent must stay alive) legislates against harness reality. Q4=D (persist verdicts) feeds prior verdict instead of prior evidence — the exact sin this spec abolishes, plus ledger-as-database. | Q4=A |
| D5 | **Playbook-verification suite location: existing suite; both fixtures as ordinary passing tests.** Issue-numbered `describe("410 — …")` block in `packages/claude-plugin-cockpit/tests/playbook-verification.test.ts` (established by #398 / #402 / #408). Q5=A (expected-to-fail as flag) normalizes red in the suite. Q5=B (new harness beside) builds a second suite for no reader benefit. Q5=D (defer) is what this plan resolves. Settled house convention. | Q5=C |
