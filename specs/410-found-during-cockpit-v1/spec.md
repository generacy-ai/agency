# Feature Specification: Found during the cockpit v1

**Branch**: `410-found-during-cockpit-v1` | **Date**: 2026-07-12 | **Status**: Draft

## Summary

Found during the cockpit v1.5 auto-mode integration smoke test (generacy-ai/tetrad-development#92), finding #62 — snappoll-1 run 11.

## Observed

On a **repeat** D.7 failure, the auto session never fetched the new failure evidence — it asserted similarity and dispatched on the assertion:

1. First failure (#3/#4 `failed:validate`): diagnosis subagents correctly identified the stale-base `npm ci` EUSAGE (branches forked pre-scaffold). Operator chose Requeue.
2. Requeue re-ran validate → `failed:validate` again within ~90s.
3. The parent's dispatch: *"Rather than re-run full diagnosis, I'll continue the two existing diagnosis subagents with the new fact (**requeue failed identically**)"* — but no one had read the new alert. The parent injected "failed identically" into the subagents' context **as fact**, and both returned Skip verdicts built on it ("requeue can't fix the stale base; needs an out-of-band branch sync").
4. Ground truth (from the fresh #915 reason-bearing alerts): the failures had **changed class entirely**. The requeue had *worked* — the #914 base-merge brought the scaffold in and `npm ci` **passed** — and the new failures were two distinct in-branch defects (#3: `@prisma/client` missing from the epic's dependency plan; #4: a source-guard test tripped by the implementation's own doc comment). "Needs out-of-band branch sync" was wrong for both; the verdicts, their confidence labels, and the escalation-gate presentation were all built on an unverified premise.

Cost: the operator was steered toward Skip (which would have wedged P1 and the epic) when the actual remedies were a one-line dependency addition and a comment reword. The misdiagnosis was caught only by out-of-band operator review of the alert comments.

## Root cause

auto.md's D.7 evidence contract covers the **first** dispatch (parent fetches the engine bundle → spawns diagnosis subagent) but is silent on the **repeat-failure** path. The session's continuation pattern (SendMessage to the existing subagent) is good — context reuse is exactly right — but the continuation prompt carried the parent's *conclusion* ("identical") instead of *evidence*. Similarity between two failures is a determination only evidence can support: the engine now ships classifier reasons and output tails in every alert (#915) precisely so this comparison never has to be guessed.

## Fix (auto.md D.7)

1. **Repeat-failure dispatch fetches fresh evidence first** — same evidence verb as the first dispatch (`cockpit_context` / the new alert body via the engine bundle). No dispatch of a repeat D.7 without the new alert in hand.
2. **The parent never characterizes the failure** — the subagent continuation receives the verbatim new evidence (alert body / reason / output tail) alongside the prior context, and *it* determines same-or-different. Parent-authored summaries of evidence are forbidden in diagnosis prompts (the loop-trust-boundary principle applied to the parent itself: assertions are advisory, evidence is authoritative).
3. **Verdict schema addition**: the diagnosis verdict gains a `failure_class_changed: boolean` field on repeat dispatches, surfaced in the escalation-gate presentation — a changed class after a Requeue usually means the requeue *made progress* and the recommendation calculus should reflect that (this incident's Skip recommendations inverted it).

## Regression coverage (playbook-verification suite)

- D.7 section text asserts the repeat-dispatch evidence-fetch requirement and the no-parent-characterization rule.
- Negative fixture: a D.7 variant whose repeat path passes a similarity assertion instead of evidence → flagged.
