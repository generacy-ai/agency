# Implementation Plan: /cockpit:watch slash command

**Feature**: Launch Claude Code's `Monitor` tool on `generacy cockpit watch` and apply the autonomy policy to each transition
**Branch**: `351-epic-generacy-ai-tetrad`
**Date**: 2026-06-26
**Spec**: [spec.md](./spec.md)
**Status**: Complete

## Summary

Ship one file — `packages/claude-plugin-cockpit/commands/watch.md` — a slash-command playbook the Claude Code agent executes when the user runs `/cockpit:watch <epic-ref>`. The playbook tells the agent to spawn `generacy cockpit watch <epic-ref>` under the `Monitor` tool (persistent, line-streamed), and for each emitted transition line: parse it, compute a local dedupe id, consult the autonomy policy, and either invoke the mapped `/cockpit:*` command (auto) or surface an inline chat notification (notify-only / unmapped). All retry/reconnect behavior is delegated to `generacy cockpit watch` itself (per #787 FR-009); this command does not implement its own retry loop. All ref resolution (`owner/repo#N` ↔ bare number) is delegated to the engine resolver (per #788); the slash command does not reinterpret refs. The deliverable is a markdown command file, not code.

## Technical Context

**Language/Version**: None compiled. The artifact is a markdown command file consumed by Claude Code's plugin loader.
**Primary Dependencies**:
- `claude-plugin-cockpit` package scaffold from #350 (provides the `commands/` directory and the `cockpit` namespace registration).
- Claude Code `Monitor` tool — spawns a long-running process and emits one notification per stdout line; reconnect/exit handling is the tool's responsibility.
- `generacy cockpit watch` (#787) — emits one JSON line per epic state transition; backs off on transient stream errors and never exits on them.
- Autonomy policy lookup (G1.1–G1.3, A1.4) — resolves a transition class to `auto` (with a `/cockpit:*` command) or `notify-only`.
- Engine ref resolver (#788) — resolves bare issue numbers via `MONITORED_REPOS`; reused by `generacy cockpit watch`.
**Storage**: None. Dedupe state is in-memory in the agent's conversation context (per Q1-B). No on-disk persistence.
**Testing**: Manual acceptance — load the plugin, run `/cockpit:watch <ref>`, drive a label transition on a monitored issue, verify exactly one inline notification per transition and that the autonomy-mapped command (or notification-only) fires per policy.
**Target Platform**: Claude Code (any OS) with the `cockpit` plugin installed and `generacy` CLI on PATH.
**Project Type**: Static markdown command (no runtime code).
**Performance Goals**: One notification per transition; no perceptible delay beyond the upstream `generacy cockpit watch` emit latency. The agent should treat baseline `from: null` lines as state-sync, not actionable transitions, so re-establishing the watch doesn't re-fire historical work (Q1).
**Constraints**:
- Single file: `packages/claude-plugin-cockpit/commands/watch.md`. No code anywhere else in this issue.
- Must not reimplement retry/backoff (Q3-D) — delegate to `generacy cockpit watch`.
- Must not resolve bare epic refs in the slash command (Q5) — pass them through to the engine resolver.
- Notification surface is **inline chat only** (Q4-B); OS `PushNotification` is deferred to A5.3 / v3.
- Unmapped transitions MUST fall back to notify-only (Q2-A) — never silently drop, never fail-fast.
- Dedupe id MUST be composed from `(repo, kind, number, from→to)` (Q1-B); baseline `from: null` lines MUST be classified as state-sync and skipped from action dispatch.
**Scale/Scope**: One epic per invocation; expected transition volume is low (single-digit per minute at most). One file, ~150–250 lines of markdown.

## Implementation Phases

### Phase 0: Confirm upstream surfaces are real
- Verify `generacy cockpit watch <ref>` exists and its stdout shape is one JSON line per transition (depends on #787 landing). If not yet available, draft the playbook against the documented contract in `contracts/transition.schema.md` and gate the issue on #787.
- Verify the autonomy-policy lookup surface from G1.1/G1.2/G1.3 + A1.4. If the resolver function/CLI isn't yet defined, gate this issue on those.
- Verify the engine ref resolver (#788) accepts the same `<epic-ref>` strings the slash command will pass through.

### Phase 1: Draft the command playbook
1. Write the YAML frontmatter: `description: Watch an epic and apply the autonomy policy to each transition` (matches the entry in the cockpit README's commands table).
2. Document the `$ARGUMENTS` contract: one positional `<epic-ref>` (either bare number or `owner/repo#N`), passed verbatim to `generacy cockpit watch`.
3. Step the agent through the playbook:
   a. Validate that `$ARGUMENTS` is non-empty; if empty, print usage and exit.
   b. Spawn `generacy cockpit watch <epic-ref>` via the `Monitor` tool. (No `--json`, `--no-baseline`, or other flags the agent can't predict — accept the stream as-is.)
   c. For each notification (one per stdout line): parse as JSON. If parse fails, log inline and continue (don't crash the watch loop on malformed lines).
   d. If `from === null`, classify as state-sync — record in the in-memory seen-set but **do not** dispatch any action or notify (Q1).
   e. Otherwise, compute `transition_id = ${repo}:${kind}:${number}:${from}→${to}`. If already in the seen-set, drop silently (dedupe).
   f. Look up the autonomy policy for the transition class. If mapped to `auto`, invoke the mapped `/cockpit:*` command with the transition payload (e.g. `/cockpit:clarify <ref>`). If `notify-only` or unmapped (Q2-A), emit an inline chat message with the transition summary and the suggested next command.
   g. Add `transition_id` to the in-memory seen-set.
4. Document the permanent-failure behavior: if the `Monitor` tool reports the spawned process exited (not just disconnected — actually exited), surface that to the user inline and prompt them to restart `/cockpit:watch`. Do not silently retry (Q3-D).

### Phase 2: Validate against the acceptance criterion
5. Manual acceptance: drive one label change on a monitored issue, observe exactly one inline notification and exactly one policy-driven dispatch.
6. Manual restart test: kill and restart the watch; verify the baseline lines re-sync state without re-firing actions.
7. Manual unmapped-transition test: introduce a transition class the policy doesn't cover; verify the agent surfaces a notify-only message (not a silent drop, not a startup failure).

## Open Risks

| Risk | Mitigation |
|------|------------|
| `generacy cockpit watch` (#787) hasn't landed by the time this issue is implemented | Implementation can land against the documented contract in `contracts/transition.schema.md`, but acceptance tests are blocked until #787 ships. Surface as a dependency block on the issue. |
| Autonomy policy resolver (G1.1–G1.3, A1.4) returns a different shape than assumed | The playbook only needs `(class → 'auto' | 'notify-only', optional command name, optional arg template)`. If the actual resolver returns more or less, update `contracts/autonomy-policy.schema.md` and the lookup step in the playbook. |
| Engine ref resolver (#788) rejects refs `generacy cockpit watch` accepts (or vice versa) | Both paths must accept the same `<epic-ref>` strings. If they diverge, raise back to #788 — do not paper over in this slash command. |
| `Monitor` tool's reconnect semantics conflict with #787's "never exits on transient errors" guarantee | Trust #787 first. If `Monitor` itself terminates the spawned process on a transient error, treat that as a permanent-failure surface and prompt the user to restart. Do not reimplement retry. |
| The agent re-fires actions on a watch restart because it didn't recognize a `from: null` line as baseline | The playbook step (d) is explicit; the contract in `transition.schema.md` documents the baseline marker. Acceptance test 6 verifies this directly. |
